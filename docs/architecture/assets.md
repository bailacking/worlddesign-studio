# 项目与资源

## 项目存储

通用平台项目的首轮契约草案与样例见 [项目目录与清单](project-format.md)。以下 M0 契约适用于前期原型。

项目采用普通文件夹保存源材料，并通过 WDS 资源管理获得身份、依赖、导入与索引能力。用户应能使用外部编辑器检查和编辑源文件；缓存和自动说明可重建，不应成为唯一资料副本。

具体目录、元数据格式和存储机制尚未选型。源内容、配置、可重建缓存、临时产物与发行产物需要区分；移动整个项目后应能够重新定位内部资源。

## 资源身份与文件路径

资源使用稳定编号和文件路径共同管理：编号表达身份，路径表达当前位置及人类可读的组织方式。改名和移动不应导致引用丢失。

编号生成、复制语义及映射存储待评估。复制文件时需判断产生新资源还是同一资源的新版本；跨项目导入需处理编号冲突；删除、恢复和重新索引不得静默覆盖另一资源。内容哈希可以校验内容，是否用于身份必须单独论证。

## 多种编辑形式

同一资源可提供文本、结构化数据或可视化等不同编辑形式，但各资源类型必须定义权威内容、编辑视图和派生产物的关系。

场景的图形视图和结构化视图可以共同编辑同一语义模型；纹理原图与目标平台压缩纹理通常是源与派生关系。图片、音频和模型无需被强制转换为纯文本。转换不能无损完成时，应提示损失、保留原始内容并允许取消。

## 修改与冲突

| 资源类型 | 可研究的策略 | 必须保留的保障 |
| --- | --- | --- |
| 文本与代码 | 基于共同修订的差异合并 | 冲突可见，保留双方修改与基础版本 |
| 场景、材质、逻辑图 | 基于稳定节点或字段的结构化合并 | 区分同字段冲突、删除与引用变化 |
| 图片、音频、模型等二进制内容 | 锁定、版本分支、选择或专用合并工具 | 不以最后写入静默覆盖；保留可恢复副本 |

具体策略由资源插件声明并验证。多人、AI 与外部工具造成的变更都应进入修订和冲突检测，不能只观察编辑器内操作。

### M0 项目保存契约

M0 项目由普通源文件、可读的项目清单和同目录事务记录组成。清单保存项目修订号以及资源 ID、相对路径和引用 ID。修订号从 0 起，成功修改才递增。首次打开时验证清单完整性，拒绝重复 ID、重复路径和无法解析的引用。索引由清单派生。

试行格式见 [样例清单](../../examples/m0-project/.wds-project)。首行写 `wds-project-v1 <修订号>`，每行一个资源，字段依次是 ID、相对路径及零个或多个引用 ID。字段以空白隔开。根目录的 `.wds-rename` 记录改名事务，`.wds-project.tmp` 和 `.wds-rename.tmp` 是保留的暂存名。事务使用 FNV-1a 64 位校验值识别意外变更。

首轮只在本机文件系统内验证同目录文件改名。路径各段与新文件名使用 ASCII 字母、数字、下划线、短横线和点，首字符为字母或数字，拒绝尾点和 Windows 保留设备名（含带扩展名的形式）。禁止绝对路径、父目录跳转和经过符号链接或重解析点的路径。目标与磁盘和清单上的现有路径均按 ASCII 大小写不敏感比较，实际改名保留提交的拼写。M0 同一项目只允许一个写入者，测试期间外部工具不同时写入项目。

写入顺序为：验证来源与目标 → 写入并校验可重开的事务记录 → 移动源文件 → 提交完整新清单 → 清理记录。记录至少含旧、新修订号、资源 ID、两个路径及旧源文件校验值。清单提交是操作生效点。事务记录和清单各自在同目录完整写入临时文件再提交，按平台能力验证操作失败后留下的文件。Windows 与 POSIX 的文件替换条件和失败行为需分别核对。[Windows ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) · [POSIX rename](https://pubs.opengroup.org/onlinepubs/9799919799/functions/rename.html)

| 重开时观察到的状态 | 恢复行为 |
| --- | --- |
| 旧清单完整，旧路径仍是原文件，新路径空闲 | 保留旧修订并清理事务记录 |
| 旧清单完整，旧路径空闲，新路径是原文件 | 校验文件后移回旧路径，保留旧修订并清理记录 |
| 新清单完整，只有新路径，且文件与记录匹配 | 保留新修订并清理事务记录 |
| 清单无法判定、路径冲突或文件校验不符 | 保留现场，返回恢复诊断，阻止后续写入 |

若修订状态已确认，但事务记录清理失败，允许读取已确认修订并返回诊断，暂停写入，重开时重试清理。恢复动作要可重复，恢复源文件时禁止覆盖现有文件。验收范围为进程中断和可注入写入失败。断电持久性、多进程竞争和网络文件系统另行评估。

**联调样例**：初始修订号 0，资源 `A` 路径 `assets/scene.txt`，引用资源 `B`；`B` 路径 `assets/tile.txt`。用两份同样的初始项目分别走 GUI 与 CLI，将 `B` 改名为 `stone.txt`。保存重开后修订号为 1，`B` 位于 `assets/stone.txt`，源字节不变，`A` 仍引用 `B`。再用修订号 0 提交，应返回 `revision_conflict`。在移动后、提交前模拟中断，应恢复修订号 0；提交后、清理前模拟中断，应保留修订号 1。再重开一次确认状态保持一致。

## 项目说明与索引

自动整理的说明提供资源关系、关键逻辑、运行方法与已知问题，并关联源文件、资源编号、生成修订及失效状态。原始文件和说明共同帮助理解项目；发生不一致时，依据源内容与资源契约核对并重建说明。

增量更新应考虑移动、删除、文件监视遗漏及二进制内容变化。索引损坏时应能够从源文件和有效元数据重建。AI 生成的说明不可自动成为改写源内容的依据。

## 验证标准

验证改名、移动、复制、跨项目导入、大小写变化、删除恢复和重复编号；删除可重建缓存后重新打开项目；两种编辑形式交替修改并重开；并发修改分别覆盖文本、结构化和二进制案例。
