# 插件与组合

## 设计目标

WDS 的具体功能尽可能由插件提供。用户可以安装、卸载、替换和配置能力；默认发行组合提供完整、经过验证的基础创作体验。所有贡献者使用公开规则，默认组合的维护职责不赋予插件天然更高的评价。

M0 插件宿主实现了本页的最小宿主契约。动态插件框架、运行边界及清单格式待技术评估。

## 能力契约

每项可替换能力明确三个角色：**接口定义**规定语义与版本；**能力实现**提供具体行为；**调用方**通过接口使用能力。插件可以承担多个角色，但依赖关系必须可见。

直接执行任务使用明确服务方法，观察状态与扩展策略使用明确事件。事件契约应说明是否等待、监听顺序、错误传播、返回值和是否允许中断；不要让同一事件名隐含多种调度规则。

同一能力的多个实现应显式选择，或通过规定的组合规则协作。不得依赖加载顺序静默覆盖。接口版本稳定性、弃用范围与迁移方式应对使用者可见。

## 插件元信息

清单至少需要表达身份、版本、契约版本范围、支持平台、编辑器或游戏运行用途、提供和需要的能力、依赖、已知冲突、权限、配置及数据迁移要求。具体字段和格式未定。

版本声明解决版本准入问题，不证明行为兼容或安全。安装、导入、启动、正常运行与卸载是不同阶段，应分别验证。

## 生命周期与资源归属

插件经历发现、预检、装配、启动、运行、停止、清理和卸载。每个服务注册、监听、定时器、后台任务、文件句柄和图形资源应有明确所属者与释放路径。初始化部分成功后失败，也必须能够清理已取得的资源。

停用时先阻止新任务，再取消或等待已有工作，处理依赖方，最后释放资源与注册。不能安全热卸载的插件应声明需要停止游戏或重启，不以热更新作为普遍承诺。

### M0 插件宿主契约

M0 以同进程、随程序编译的可信试验插件验证装配。插件由宿主显式注册，声明插件 ID、提供的能力、依赖的插件 ID，以及本次组合中是否必需。用两个插件验证：`project-store` 提供项目存取能力，`asset-commands` 依赖它并提供共享操作。GUI 和 CLI 由外部适配入口调用共享操作。

- **预检**：按依赖拓扑排序，同层按插件 ID 排序。重复 ID、依赖闭环或同一能力有多个未明确选择的提供者时，整个组合启动失败，初始化次数为零。缺依赖的插件和依赖它的插件不启动。若其中有必需插件，整个组合预检失败。
- **启动与发布**：依赖先于使用方启动。插件只读取已启动依赖的能力。宿主在插件初始化成功后发布它的能力。插件初始化报告失败时，先释放它已登记的资源，再记录失败。依赖方被标为未启动，并携带上游原因。
- **就绪**：全部必需插件就绪才可开放工作流。可选插件失败时，独立且健康的能力继续提供服务，工作流状态显示降级。必需插件启动失败时，按启动顺序的逆序关闭已启动插件，工作流返回启动失败。
- **停用**：有已启动依赖方时拒绝单独停用提供方，现有状态保持完整。关闭组合时停止接收新操作，等待当前同步操作结束，再逆序停止。每个已登记的清理动作按登记逆序执行一次，失败也继续清理其余资源并报告。清理失败后需重启宿主再尝试启动。

验收记录至少列出插件 ID、阶段、结果和依赖原因。测试使用可注入失败与记录调用顺序的试验对象，覆盖正常顺序、必需依赖缺失时零初始化、必需启动失败后逆序清理、可选失败后独立能力继续、拒绝停用及正常关闭。可选失败和逆序清理用例可在宿主测试中注入额外试验对象。动态加载、热卸载、并发回调和跨编译器二进制兼容独立验证。

## 组合与配置

区分插件包、可安装的组合包和用户工作配置。组合包表达一组能力与默认配置；工作配置表达某个项目或用途最终选择的组合。

建议按“发行默认值 → 工作配置 → 项目设置 → 用户本机覆盖 → 启动参数覆盖”研究有序合成。该顺序尚待原型评审，特别要确定哪些设置允许项目或用户覆盖。覆盖规则、替换与合并语义必须明确，并提供最终配置及来源的只读检查。

可分享组合应记录可重现的版本、依赖和平台条件，区分配置意图、已安装版本与当前运行状态。凭据和机器私有路径不进入共享组合。默认组合、2D/3D 专用组合、AI 创作组合及极简组合是可研究的发行形式。

## 兼容性与失败处理

| 情况 | 要求 |
| --- | --- |
| 版本不匹配、依赖闭环、重复身份 | 尽可能在加载前阻止，并说明具体冲突与处理选项 |
| 可选能力启动失败 | 明确降级及受影响任务，其他独立能力尽可能保持可用 |
| 当前工作流所必需的能力失败 | 不得展示虚假的就绪状态；进入诊断、修复或安全启动 |
| 配置无效 | 不破坏仍可用的状态，报告错误位置和可恢复配置 |
| 同进程原生插件崩溃 | 不承诺靠异常捕获实现硬隔离；依靠运行边界与恢复设计处理 |
| 依赖方仍在使用插件 | 拒绝不安全卸载，或按明确策略停止依赖方 |
| 缺少热更新支持 | 保存后明确标记需要重启，不能将“已保存”显示成“已生效” |

安装前检查、契约测试、默认组合测试、重点组合验证与用户复现案例共同降低冲突，不能覆盖任意插件组合的全部行为。

## 更新与恢复

更新应分为准备、预检、安装、激活、验证与完成等可观察阶段。保留原版本、配置、依赖状态与受迁移影响的数据；各阶段失败后给出实际处置状态，而非笼统显示“已回滚”。

数据迁移必须有备份或可验证的恢复路径。恢复清单和锁文件不必然恢复实际安装内容；恢复安装内容也不必然恢复外部副作用。诊断应区分恢复完成、需重启、需重新安装及需人工恢复。

## 权限、打包与生态

声明文件、网络、外部程序和系统资源权限，并由真实执行边界约束。插件安装不能默认为无限权限；安装脚本与插件运行权限需分别考虑。兼容性豁免若未来提供，应限定具体版本组合，并标注其未经正常准入验证的状态。

编辑器插件和游戏运行插件具有不同权限、生命周期与打包要求；导出只包含必需的运行闭包及相应许可声明。

用户可以评分、评论、报告问题和分享组合。受欢迎程度与兼容性、安全报告、权限、维护活跃度分别呈现。治理规则见 [社区治理](../community/governance.md)，验证方法见 [质量与验证](../engineering/quality.md)。
