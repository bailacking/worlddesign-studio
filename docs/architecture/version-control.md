# 版本管理

## 目标与方案状态

版本管理应帮助创作者理解变更、恢复可用状态并协作处理游戏资源。**深度整合 Git、增加游戏开发能力是候选方向，具体方案尚未确定。** 不预设已实现 Git 适配层、服务器或大文件服务。

## 操作边界

本地保存、版本检查点、Git 提交、远程推送和发布属于不同操作。应分别显示目标、范围和结果，避免把保存动作隐式升级为对外同步。AI 使用相同权限与状态规则。

## 资源差异与合并

代码与文本需要可读差异；场景与逻辑图可研究语义比较；图片、音频与模型需保留版本并按资源类型提供比较或锁定机制。稳定资源编号帮助识别改名与移动，但不能自动解决内容冲突。

采用 Git 时，应维持真实仓库状态与界面一致，避免自建历史界面成为唯一权威来源。合并冲突应保留基础版本与双方修改，关联资源身份和失效引用。

## 大文件与协作

比较普通 Git、大文件扩展与外部资源存储的适用边界，包括离线使用、存储与带宽成本、克隆和恢复、服务可替换性。任何收费服务、账号或外部存储都不是当前既定依赖。

## 评估与验收

使用包含代码、场景、二进制资源的样例验证差异、分支、改名、合并、恢复和断网使用。比较轻量 Git 调用与深度工作流整合的成本；在证据充分前保留其他可行方案。
