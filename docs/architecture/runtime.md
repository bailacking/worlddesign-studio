# 游戏运行时

## 2D 与 3D

2D 与 3D 共享通用逻辑、资源身份和可复用的行为概念，渲染、物理与空间处理分别优化。共享范围需以实际场景验证，不要求所有三维行为都可直接用于二维。

早期 3D 方块沙盒验证了独立运行。通用项目支持 2D 试玩与 3D 方块编辑，两者使用同一个工作台和项目清单。正式渲染后端、物理库和脚本运行机制仍在评估。

## 场景与试玩会话 v1

通用项目通过 `entry_scene` 指定入口场景资源。场景 JSON 使用独立的 `format_version`，当前为 1。场景中的实体按数组顺序初始化。

```json
{
  "format_version": 1,
  "entities": [
    {"id": "origin"},
    {"id": "marker", "x": -260, "y": -25, "vx": 1}
  ]
}
```

- 实体 ID 在场景内唯一，遵循项目 ID 的字符规则。`x`、`y` 为 2D 位置，`vx`、`vy` 为每个运行步的位移。四个字段均为 −1,000,000 到 1,000,000 的整数，省略时为 0。
- 当前上限为 1 MiB、1024 个实体和每会话 600 步。未知字段、重复 ID 和不受支持的版本会阻止试玩。旧项目的空对象 `{}` 作为空场景加载，新建项目使用显式的空实体数组。
- 启动时校验项目并比较调用方提供的修订号，再把入口场景加载到内存。运行状态只保留在会话中。停止后重新启动会重新读取磁盘，位置从源数据重新计算。修订号用于检测 WDS 提交的变化，直接在磁盘编辑 JSON 时需重新启动试玩。
- CLI 的 `project play` 推进指定步数后返回快照。工作台和试验播放器按单调时钟累计 1/30 秒的固定步，单次更新最多计入 250 毫秒。渲染读取会话快照。达到 600 步或触发结局后停在最后一帧，停止后可重新启动。打开、恢复、切换目录或成功提交字段会结束当前会话。

### 二维精灵与试玩规则

- 实体可声明 `box: {"half_width": 13, "half_height": 16}`。两个值均为 1 到 1,000,000 的整数，矩形以实体坐标为中心。可同时声明 `sprite: "courier"`，指向入口场景资源 `refs` 中的 PNG 图片 ID。按实体数组顺序绘制，后画的在上。会话在启动时读取并冻结 PNG 像素，去重后最多 32 MiB RGBA 数据。缺失引用或坏图返回资源路径与字段位置。
- 场景可声明 `play: {"player": "courier", "speed": 6, "walls": ["barrier"], "goals": ["signal-station"], "hazards": ["shallow-reef"]}`。各角色使用不同实体，均需声明碰撞框且源速度为零。至少有一个目标，墙和危险区可为空。玩家出生时不能与墙重叠。速度是每步每轴 1 到 256 个世界单位。其他实体仍使用原有整数位移。
- 默认以 WASD 或方向键移动。可在 `play.keys` 中为 `left`、`right`、`up`、`down` 各配置非空数组，支持大写 A–Z 及 `Left`、`Right`、`Up`、`Down`，同一个键只绑定一次。两个同向键同时按下仍移动一步，相反方向抵消。失焦会清键并暂停，恢复后需重新按键。
- 每步先沿 X，再沿 Y 移动。玩家与静止墙体发生扫掠碰撞时贴边停下，接触边缘可以沿墙滑行。经过目标触发成功，经过危险区触发失败，同一步遇到两者时失败优先。600 步内未抵达时以超时结束。CLI 无真人输入，交互场景额外返回 `outcome`（`playing`、`won`、`lost`、`timed_out`）。

## 通用工程的 3D 方块场景

`wds.project.json` 仍使用版本 1。入口场景的 `kind` 为 `voxel`，`materials` 引用入口场景 `refs` 中的一个 `text` 资源。材质沿用下方方块内容格式，包含天空、默认放置方块、各材质颜色和可破坏规则。示例工程见 [方块工坊](../../examples/voxel-workshop/README.md)。

省略 `terrain` 和 `world` 时生成原型的 24 × 12 × 24 固定地形。声明种子地形后，运行时在玩家周围流送区块，存档保留相对种子的改动。 [种子地形格式](../project/w13-worlds.md#方块世界)

原型地形保存后，场景的 `world` 字段记录 `wds-voxel-v1` 地形，保存使用已有项目修订和场景事务。过期修订或场景原文已变时返回冲突。相机位置和操作中尚未提交的方块保留在内存，重新启动回到出生点和已保存地形。

第一人称相机、拾取和移动复用原型的方块规则。使用屏幕中心射线在 7 格内拾取，放置发生在命中面的相邻格。地基、玩家碰撞和出生点约束沿用原型。3D 方块工程在工作台直接编辑。独立播放器与 Windows 导出当前支持 2D 场景。

## M1 方块原型

首轮使用 24 × 12 × 24 的有限方块世界。C++ 模型负责方块、玩家包围盒、重力和逐轴碰撞，Windows 窗口通过 CPU 射线绘制第一人称画面。准星的射线在 7 个方块的范围内选择目标，放置使用可见面相邻的空格。底层地基保持完整，放置会避开玩家和出生点。

运行存档记录当前地形。读取时校验版本、尺寸、所有方块和出生点，再一次性应用。Windows 使用同目录暂存文件提交存档，坏档保留原文件。后续图形后端和项目资源集成独立评估。[运行步骤](../engineering/development.md#运行方块沙盒)

## 方块项目内容

项目目录中 `sandbox-content-v1.txt` 保存配色、方块破坏规则和默认放置方块。格式如下，每项出现一次：

```text
wds-sandbox-content-v1
sky e9af8b
place dirt
grass c89351 breakable
dirt b66a43 breakable
stone 774a55 locked
```

颜色使用六位 RGB 十六进制。方块 ID 为 `grass`、`dirt`、`stone`，可破坏状态为 `breakable` 或 `locked`。老项目缺少该文件时沿用默认草地配置，已有地形存档的方块 ID 保持兼容。内容文件格式错误会阻止显式项目启动。运行时仍使用同一组有限地形与方块 ID。

## 能力划分

运行能力包含场景与实体、渲染、输入、物理、音频、动画、地形、资源装载及网络等。每项能力明确接口、实现、依赖和更新时机；可复用成熟组件，也可为必要边界编写适配。

实时路径应关注帧时间、内存、线程、资源所有权和调试能力。插件化不能意味着所有逐帧数据都必须通过通用消息总线或网络传输，热路径与管理路径可以采用不同机制，但语义需一致。

## 编辑状态与运行状态

编辑器保存源项目，运行时使用有效场景与资源。运行中修改、停止后的状态保留、热重载与调试映射应逐项定义，不假定所有状态都自动同步或持久化。

2D/3D 共享逻辑需要分别通过样例确认；编译和启动成功不能替代物理、交互与视觉检查。联网能力另需研究同步、权威状态、延迟和恢复，不纳入首个沙盒闭环的必要范围。

## 构建与导出

导出选择目标平台资源和必需运行插件，形成可独立运行的游戏。编辑器工具、开发密钥、临时资料与无关插件不应进入成品。随包保留相关第三方许可与归属声明。

完整导出还需验证资源引用、路径、保存位置、启动入口和运行依赖，不能将编辑器内预览当作独立发行产物。

## 首个运行验收

完成地形、移动、方块放置与破坏、保存重开及规则修改的流程，记录实际平台和限制。帧率、加载时间、内存与资源规模应附测量环境和方法，目标值在原型基线建立后确定。
