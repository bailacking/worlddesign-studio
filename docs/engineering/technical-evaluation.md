# 技术评估

## 评估状态

语言、框架、协议与关键数据结构尚未完成选型。以下问题按系统领域组织，以可复现实验收敛，不通过文档措辞预先确定技术路线。

| 领域 | 需要回答的问题 | 比较重点 | 最小证据 |
| --- | --- | --- | --- |
| 语言与工具链 | 核心、编辑器、脚本是否采用同一语言 | 性能、构建调试、插件边界、跨平台、贡献门槛 | 同一插件与操作样例的运行和维护成本 |
| 运行基础 | 自研哪些边界，复用哪些组件 | 接口稳定性、许可、适配与退出成本 | 一个完整装配与停止流程 |
| 插件隔离 | 进程内、进程间或受限运行环境如何分工 | 实时开销、资源归属、权限执行与恢复 | 两插件及依赖方的故障注入 |
| 操作契约 | 事务、重试、长任务与取消怎样表达 | 一致性、可诊断性与外部副作用 | 等价操作、并发冲突与取消后的最终状态 |
| 项目资源 | 编号、路径与元数据怎样持久化 | 复制导入、索引重建、外部修改 | 改名、重复编号、丢索引后的恢复 |
| 逻辑编辑 | 代码与可视化共享到哪一层 | 可互转子集、调试映射和信息保留 | 往返转换与行为等价样例 |
| 多形式资源 | 哪份内容权威、何时转换与合并 | 资源类型、数据损失与并发 | 三类资源冲突和恢复 |
| 运行系统 | 渲染、场景、物理与输入如何复用 | 2D/3D 边界、线程、图形与包体 | 方块交互场景和共享逻辑样例 |
| Git 整合 | 轻量调用还是深度工作流整合 | 大文件、语义差异、离线与服务成本 | 含二进制资源的分支合并与恢复 |
| 平台范围 | 首期平台及 Web 场景如何排序 | 文件、图形、插件与工具链限制 | 明确设备与未验证项的平台矩阵 |
| AI 协作 | 自主程度、上下文、预算与提供商如何组合 | 过时信息、授权、停止与可接管性 | 相同任务在不同权限范围下的行为 |
| 插件生态 | 发现、组合分享、评价与维护如何实现 | 可复现版本、透明规则和弃维护交接 | 两个替代插件的安装、替换和恢复 |

## 首轮顺序

先收敛语言与工具链候选、插件生命周期、共享操作和资源身份；同时识别跨平台约束。再围绕首个沙盒确定运行组件和 AI 接入。代码与可视化、多形式资源和生态机制可以先做契约研究，避免后期接口冲突。

## 形成结论的条件

每项评估给出范围、至少一个可行替代方案、实际实验、失败条件、许可与平台影响、迁移或退出办法。资料介绍、源代码观察与运行结果分别标注。未执行的实验不计为验证。

产品层面的取舍应转化为清晰选项，例如 Web 首先覆盖试玩还是创作、默认组合覆盖哪些任务；同时附工程代价，使选择可以基于证据完成。
