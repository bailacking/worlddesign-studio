# 技术评估

## 引擎核心语言

引擎核心使用 **C++**。C++ 拥有成熟的游戏开发生态，AI Agent 能协助开发，也有利于吸引专业引擎开发者参与。WDS 可以评估并复用成熟的图形、物理、音频和网络库。C++ 适合高性能、跨平台与长期开发的目标，具体表现以实测为准。

具体 C++ 标准、编译器支持范围、构建工具、依赖管理、测试工具和第三方库待调研。编辑器界面、项目脚本及外部工具的语言可按各自边界独立评估。选型优先满足需求、兼容性与维护成本，允许未来按模块替换经过验证的实现。

## 首轮工具链调研

| 调研项 | 要回答的问题 | 所需证据 |
| --- | --- | --- |
| 标准与编译器 | 首轮用到哪些标准特性，各目标工具链能稳定支持到哪一版 | 用同一最小样例记录编译器版本、标准选项、警告、构建及运行结果 |
| 构建、测试与 CI | 新贡献者怎样复现构建、测试、调试和静态检查 | 从干净目录复跑配置、构建、测试和检查，记录环境、命令与失败情况 |
| 依赖管理 | 如何固定版本、复现安装、跟踪许可，并替换不再适用的库 | 对一个试验依赖验证获取、固定版本、升级和恢复，记录许可与分发约束 |
| 第三方库 | 各领域是否满足能力、性能、平台覆盖和接入边界 | 按图形、物理、音频、网络等领域分批比较。先调研首个原型直接依赖的库，其余随里程碑推进 |

使用至少两套可行的 C++ 工具链组合，跑同一个小样例：装配试验模块、从两个入口执行等价操作、保存并重开数据。记录工具版本、复跑步骤、实测平台、失败和未覆盖平台，给出最低适用标准、推荐方案与替代方案。样例用于评估，正式项目的公共接口仍以契约评审为准。

### 本机工具链基线

在 Windows x64 上通过 Visual Studio 2022 Build Tools 的 x64 开发者命令环境完成一次最小构建。实测 MSVC 19.44.35228.0、随附的 CMake 3.31.6-msvc6 和 Ninja 1.12.1，Windows SDK 目录中有 10.0.26100.0。普通 PowerShell 的 PATH 中没有这些构建工具，复跑时使用已安装的开发者环境，并把随附的 CMake 和 Ninja 加入该终端的 PATH。

在临时目录建一个只含 `int main() { return 0; }` 的 C++ 程序，用构建文件声明可执行目标并注册一个运行该程序的测试。实测使用 C++20 模式，关闭编译器扩展并要求标准生效。然后执行：

```sh
cmake -S . -B build -G Ninja
cmake --build build
ctest --test-dir build --output-on-failure
```

配置、编译和 1 项测试通过。此结果验证单个环境可用。跨平台、依赖管理、插件装配、共享操作和保存仍需实测，标准与工具链仍待评审。[MSVC 标准选项](https://learn.microsoft.com/en-us/cpp/build/reference/std-specify-language-standard-version?view=msvc-170) · [CMake 标准属性](https://cmake.org/cmake/help/latest/prop_tgt/CXX_STANDARD.html) · [CTest 手册](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

### 首轮试行基线

建议用 **C++20、CMake 3.25 起、Ninja、CTest** 搭建首个构建骨架。C++20 模式已通过 Windows MSVC 实测，`std::span` 可用于传递非拥有的参数序列。CMake 3.25 是本轮预设配置的目标下限，实际测试用的是随附的 3.31.6。CMake 预设让本地与 CI 共享命令，Ninja 可生成供分析工具使用的编译数据库。CTest 足以运行骨架测试，首批测试只使用标准库。[CMake 预设](https://cmake.org/cmake/help/v3.25/manual/cmake-presets.7.html) · [编译数据库](https://cmake.org/cmake/help/v3.25/variable/CMAKE_EXPORT_COMPILE_COMMANDS.html)

在 Windows x64 使用 MSVC 19.44 和同一组临时样例，对照 Ninja 1.12.1 与 Visual Studio 2022 生成器。两组均通过构建和 1 项 CTest。样例静态链接试验模块，通过模拟 GUI 和 CLI 的两个入口传入同一组参数，比较结果并写入文件后重读。它验证编译、链接、等价调用与简单读写。随附的 clang-tidy 19.1.5 能读取 Ninja 编译数据库，对样例源文件无报告，系统头诊断被过滤。

Visual Studio 生成器可作为 Windows 的备选。两组使用同一个编译器，Linux 由构建骨架 CI 补验证，macOS 仍待验证。最低 CMake 版本需另测。动态插件、故障恢复、依赖管理和第三方库随相关任务评估。

## 其他开放问题

| 领域 | 需要回答的问题 | 比较重点 | 最小证据 |
| --- | --- | --- | --- |
| 运行基础 | 自研哪些边界，复用哪些组件 | 接口稳定性、许可、适配与退出成本 | 一个完整装配与停止流程 |
| 插件隔离 | 进程内、进程间或受限运行环境如何分工 | 实时开销、资源归属、权限执行与恢复 | 两插件及依赖方的故障注入 |
| 操作契约 | 事务、重试、长任务与取消怎样表达 | 一致性、可诊断性与外部副作用 | 等价操作、并发冲突与取消后的最终状态 |
| 项目资源 | 编号、路径与元数据怎样持久化 | 复制导入、索引重建、外部修改 | 改名、重复编号、丢索引后的恢复 |
| 逻辑编辑 | 代码与可视化共享到哪一层 | 可互转子集、调试映射和信息保留 | 往返转换与行为等价样例 |
| 多形式资源 | 哪份内容权威、何时转换与合并 | 资源类型、数据损失与并发 | 三类资源冲突和恢复 |
| 运行系统 | 渲染、场景、物理与输入如何复用 | 2D/3D 边界、线程、图形与包体 | 方块交互场景和共享逻辑样例 |
| Git 整合 | 轻量调用还是深度工作流整合 | 大文件、语义差异、离线与服务成本 | 含二进制资源的分支合并与恢复 |
| 平台范围 | 首期平台及 Web 场景如何排序 | 文件、图形、插件与工具链限制 | 明确设备与未验证项的平台矩阵 |
| AI 协作 | 自主程度、上下文、预算与提供商如何组合 | 过时信息、授权、停止与可接管性 | 相同任务在不同权限范围下的行为 |
| 插件生态 | 发现、组合分享、评价与维护如何实现 | 可复现版本、透明规则和弃维护交接 | 两个替代插件的安装、替换和恢复 |

## 首轮顺序

并行调研 C++ 工具链，并约定插件生命周期、共享操作和资源身份。先识别首个可复现环境和跨平台约束，再围绕首个沙盒逐步确定运行组件和 AI 接入。

## 形成结论的条件

每项评估给出范围、至少一个可行替代方案、实际实验、失败条件、许可与平台影响、迁移或退出办法。资料介绍、源代码观察与运行结果分别标注。未执行的实验不计为验证。

产品层面的取舍应转化为清晰选项，例如 Web 首先覆盖试玩还是创作、默认组合覆盖哪些任务；同时附工程代价，使选择可以基于证据完成。

## 编码前的验收条件

1. 评审首轮工具链报告，明确适用的 C++ 标准、构建与测试入口、首个验证平台和未验证范围。
2. 评审插件、共享操作和保存的最小契约，明确失败行为和集成验收。对原型直接依赖的第三方库确认其版本、许可与替换边界。
3. 构建骨架可按试行基线先搭建。按评审结论分配 [首批引擎实现任务](../project/development-tasks.md)，把格式、静态分析和行为测试接入已有构建检查，再并行实现插件宿主、项目存取与共享操作。
